# 测试策略：Vitest 单元 + Playwright 真实浏览器 E2E

纯逻辑（地图生成、掉落与奖励抽取、经济公式、技能槽与配方校验、存档序列化往返）用 Vitest 在 Node 中覆盖。集成与 UI **不做 jsdom 可行性验证，直接走 Playwright 真实浏览器 E2E**：通过调试面板与固定 RNG 种子铺设前置状态，覆盖模式启动、完整战斗、奖励三选一、商店、技能槽替换、存档恢复、Boss 阶段转换，并对关键面板做截图快照。CI 使用独立工作流（`paths: general-soul-samsara/**`），执行 lint + Vitest + Playwright（chromium，带缓存）。

## 备选方案

- jsdom / happy-dom 集成层：更快，但引擎依赖真实布局与异步 UI，可行性未验证，且验证失败后仍要回退到浏览器。
- 只做单元测试 + 人工试玩：成本最低，但战斗流程与存档恢复的回归无法被自动发现。

## 后果

- E2E 较慢且对 UI 改动敏感，需要稳定的测试钩子（调试面板 API、固定种子）来控制脆弱性。
- 原型期 UI 频繁变动，测试更新成本被有意接受。
